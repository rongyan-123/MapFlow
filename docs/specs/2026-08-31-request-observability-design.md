# MapFlow 请求观测面板设计

日期：2026-08-31  
状态：用户已批准进入实现

## 1. 目标

在管理后台新增“请求观测”面板，让管理员既能排查问题，也能用可视化方式学习一条请求如何穿过 MapFlow 后端。

第一版记录所有 `/api/*` 业务请求，但排除健康检查、静态资源以及请求观测面板自身的查询请求。邀请码、注册登录、树生成和知识聊天提供比普通接口更细的内部阶段。

面板必须同时回答：

1. 请求从哪里进入、依次经过哪些模块或运行单元。
2. 哪些阶段实际经过，哪些阶段未经过或不适用。
3. 请求在哪一层被拒绝或失败，由谁作出决定。
4. 每个阶段花了多久，最终返回什么 HTTP 结果。
5. 面向新手的人话解释是什么，脱敏后的原始技术诊断又是什么。

## 2. 不做的事情

- 不记录密码、Cookie、Authorization、CSRF Token、API Key、数据库连接串或邀请码明文。
- 不记录完整请求体或响应体；“原始信息”指脱敏且有大小上限的技术诊断，不等于原样复制所有输入。
- 不把现有业务审计日志改造成请求日志。业务审计和请求观测继续保持两个独立概念。
- 不在 2 GB 服务器上引入 Grafana、Loki、Tempo、Elasticsearch 等额外常驻服务。
- 不为了画图虚构系统中不存在的 Controller 或容器。Axum route handler 在界面中标为“HTTP 处理器（类似 Controller）”。

## 3. 方案比较

### 方案 A：应用内观测模块 + PostgreSQL（采用）

Axum 入口中间件创建请求上下文，各关键模块向一个小接口追加阶段，响应完成后异步写入 PostgreSQL。管理 API 提供列表和详情，前端绘制固定路线与实际路线。

优点：数据结构稳定、可筛选、可关联业务错误、资源占用可控。缺点：需要在关键业务缝隙中显式埋点。

### 方案 B：扩展现有 `identity_audit_events`（不采用）

优点：改动少。缺点：会混淆业务审计与 HTTP 生命周期；成功请求、耗时、未经过阶段及跨运行单元关系很难准确表达。

### 方案 C：OpenTelemetry + 专用可观测性平台（暂不采用）

优点：跨服务能力最强。缺点：部署和维护复杂，在当前 2 GB 服务器上性价比过低。未来服务数量明显增加时可以迁移。

## 4. 请求身份与可信证据

每条请求拥有一个 `request_id`。Caddy 使用官方 `{http.request.uuid}` 占位符生成 ID，并通过 `reverse_proxy header_up` 覆盖传入的内部标识头，避免客户端伪造。应用只在“直接对端是已配置的可信代理，并且代理标识头正确”时，把 Caddy 阶段标记为已确认；否则标记为“未确认/直连”。

如果请求没有可信代理 ID，应用自行生成 UUID。响应统一回传安全的 `X-Request-Id`，使浏览器报错、管理面板和服务端记录可以互相定位。

Caddy 官方能力依据：

- https://caddyserver.com/docs/json/apps/http/ (`{http.request.uuid}`)
- https://caddyserver.com/docs/caddyfile/directives/reverse_proxy (`header_up`)

## 5. 后端模块

新增一个深模块 `request_observation`，对业务代码只暴露小接口：

- 创建请求观测上下文。
- 开始、通过、拒绝、失败、跳过或挂起一个阶段。
- 附加经过白名单和大小限制的结构化诊断。
- 在响应结束时提交完整快照。

存储实现是 PostgreSQL adapter；测试使用内存 adapter。业务处理器不知道表结构，也不直接执行观测 SQL。

观测写入不位于业务请求关键路径：完整快照进入有界队列，由单个后台任务写库。队列满、数据库忙或观测写入失败时丢弃观测记录并增加内部丢弃计数，绝不能拖慢或打挂真实业务请求。

## 6. 固定生命周期模型

详情页始终绘制完整节点，不因本次没有经过而隐藏：

1. 客户端 / 浏览器
2. Caddy 入口
3. MapFlow HTTP 路由
4. 通用安全守卫（来源、CSRF、请求格式、大小限制等）
5. 身份与权限校验
6. HTTP 处理器（类似 Controller）
7. 业务服务
8. PostgreSQL
9. Worker / 队列
10. 外部依赖（模型、搜索、Turnstile 等）
11. HTTP 响应

状态语义：

- `passed`：绿色，已实际经过并完成。
- `rejected`：红色叉号，规则主动拒绝。
- `failed`：橙红色，非预期错误。
- `pending`：蓝色，已移交异步处理，任务仍可能继续。
- `not_reached`：灰色，原本可能经过，但请求在更早阶段终止。
- `not_applicable`：灰色斜线，本类请求按设计就不需要这个阶段。

`not_reached` 与 `not_applicable` 必须区分，避免“没走到”和“本来就不走”混为一谈。

每个路由族拥有一份“预期拓扑模板”。实际事件覆盖模板中的对应节点，未覆盖节点仍由模板生成灰色状态。普通 API 使用通用模板；邀请码、身份、生成和聊天拥有更细的子阶段。

## 7. 数据模型

每条完成的请求写一行摘要，阶段作为有版本号的 JSONB 快照保存，减少一次请求产生十几次数据库写入。

摘要字段包括：

- `request_id`、开始/结束时间、总耗时。
- HTTP 方法、规范化路由模板、路由族；不保存 query string。
- 最终状态码与结果分类（成功、拒绝、失败、异步）。
- 终止阶段、错误码、人话摘要。
- 有效客户端 IP、直接对端 IP、账号 ID/用户名（已知时）。
- 请求/响应字节数，仅保存数字。
- 关联业务任务 ID（例如 generation run ID），不保存用户内容。
- 生命周期 schema 版本与脱敏 schema 版本。

阶段快照包括：

- 稳定阶段 ID、显示名、运行位置、状态、开始时间、耗时。
- `explanation`：面向新手的人话说明。
- `technical`：脱敏后的原始错误码、错误类型、来源模块、有限上下文。
- `evidence`：`measured`、`confirmed_header`、`inferred` 或 `not_observed`，明确事实强度。

单条技术诊断设置大小上限，超长内容截断并明确显示 `truncated: true`。

## 8. 人话错误与原始诊断

错误展示分为两栏，二者都保留：

### 人话解释

优先根据稳定错误码和终止阶段生成。例如：

> 请求被“邀请码领取频率守卫”拒绝。系统判定这个有效 IP 在过去 24 小时内已经领取过邀请码，因此没有继续读取邀请码池。

### 原始技术诊断（已脱敏）

展示 HTTP 状态、错误码、请求 ID、Rust 错误分类、来源模块、阶段上下文和安全 JSON。原始诊断经过递归脱敏，敏感键、疑似密钥、Cookie、认证头和邀请码值均替换为 `[REDACTED]`。

无法安全判断的任意字符串默认不进入持久化诊断；使用允许列表优先于事后黑名单。

## 9. 管理 API

- `GET /api/admin/request-observations`：分页列表和过滤。
- `GET /api/admin/request-observations/{request_id}`：单条完整详情。

支持按时间、结果、状态码、路由族、终止阶段、错误码、请求 ID、账号和 IP 筛选。接口只允许管理员会话访问，返回 `Cache-Control: no-store`。

这两个读取接口自身不写入请求观测表，避免面板轮询制造无限噪声。它们仍受现有安全头、管理员认证和普通服务日志保护。

## 10. 管理界面

新增“请求观测”标签页。

### 列表视图

紧凑列展示：时间、短请求 ID、方法/路由、人话摘要、结果、终止阶段、状态码、耗时、用户/IP。颜色用于辅助，文字和图标仍完整表达状态，避免只靠颜色区分。

### 详情视图

点击一行打开右侧详情抽屉：

1. 顶部显示最终结论、总耗时、请求 ID 和关联业务 ID。
2. 中部是可横向滚动的固定生命周期时间线。
3. 下方是运行位置泳道：Caddy、mapflow-app、PostgreSQL、worker、外部服务。每条泳道始终存在；未经过时显示灰色空态。
4. 点击节点展开人话解释、证据类型、耗时和技术详情。
5. 底部提供“结构化详情”页签，以折叠 JSON 树显示脱敏原始数据，并允许复制单个字段或整份诊断。

在窄屏上时间线改为纵向，避免节点被压成不可读的小块。

## 11. 保留与资源上限

- 成功请求保留 7 天。
- 拒绝、失败请求保留 30 天。
- 全表最多保留 20,000 条，达到上限后优先删除最旧成功记录，再删除最旧拒绝/失败记录。
- 清理按低频、分批方式执行，避免长事务。
- 列表索引只覆盖实际筛选字段，不给整个 JSONB 建通用 GIN 索引。
- 前端默认手动刷新，不做高频自动轮询。

## 12. 测试策略

按 TDD 分层推进：

1. 领域测试：生命周期模板、状态转换、终止后节点填充、错误翻译和递归脱敏。
2. 中间件集成测试：成功、拒绝、失败、可信/不可信代理、排除路径、请求 ID 响应头。
3. PostgreSQL adapter 测试：持久化、过滤、分页、7/30 天清理、20,000 条上限。
4. 管理 HTTP 测试：匿名拒绝、管理员可读、详情不存在、严格查询参数、`no-store`。
5. 前端 client 测试：严格校验列表和详情响应，拒绝畸形数据。
6. 前端组件测试：所有固定节点均出现；通过/拒绝/未经过/不适用状态；人话与原始诊断同时可见；键盘和窄屏可用。
7. 生产冒烟：普通请求不因观测失败而失败；邀请码拒绝能定位到 IP 频率守卫；管理读取请求不会自我记录。

## 13. 上线顺序与回滚

1. 先部署数据库迁移。
2. 部署支持观测但默认关闭的后端。
3. 更新 Caddy 内部请求 ID/代理标识头并验证配置。
4. 开启后端观测，确认写入量、延迟和脱敏结果。
5. 部署管理前端。

后端配置开关允许立即停止采集；停止采集不影响业务请求。前端在接口不可用时显示独立错误，不影响其他管理标签页。数据库表可以保留以供排障，回滚不要求破坏性删除。

## 14. 验收标准

- 任意普通 `/api/*` 请求都能在管理页查到，排除项不会出现。
- 每条详情始终显示完整固定路线，未经过节点不会消失。
- 邀请码 24 小时限制能显示有效 IP、可信代理判断、拒绝守卫和解释，不泄露邀请码。
- 响应中的请求 ID 能精确找到管理记录。
- 同一节点同时提供人话解释与脱敏原始诊断。
- 观测数据库不可用或队列满时，业务请求仍按原行为完成。
- 记录和索引规模受 7/30 天策略与 20,000 条硬上限控制。
- 后端全套测试、前端测试、类型检查和 lint 全部通过。
