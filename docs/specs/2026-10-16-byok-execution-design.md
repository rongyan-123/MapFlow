# BYOK 执行、停止与恢复审计及修复方案

2026-10-16。前端 main `3ee4812`，后端 main `2a8728b`；固定入口检查通过。已按第二轮审计修订真实 Worker 取消、Rust 输出刷新、客户端兼容和资源释放四项约束。用户随后确认 BYOK 无法恢复的上游异常应结束本轮并释放后续发送，并追加核对负余额与重发问题；现按该确认进入独立分支实施。此前审计与本次实现证据分别留存。下列生产数据来自此前已留存的只读快照。

## 事实与根因

1. 用户所报执行的前 8 个模型调用 completed；第 9 个仍为 dispatched，没有 outcome。执行在 06:43:04.582 UTC 更新为 stopped，最后一份用量在 06:43:04.873 UTC 才保存，包含 `finish_reason: tool_calls`。没有最终聊天结果，结算 audit_only，本站现金/积分金额为空；目前该执行不在待核对视图内。
2. 普通 BYOK 上游不必提供本站使用的 `cost_rmb` 扩展。当前 7 个 BYOK 成功执行均为 no_site_charge，不需要人民币回执；原提醒共用“金额回执尚不完整”属于此前已修正的分类和文案问题。
3. 独立协议复现使用真实 `DeepSeekHarnessRuntime` 与自写 Worker fixture：prepared → dispatched → usage 后触发停止，fixture 取消收尾返回原调用 outcome。Rust 先移除接收注册，晚到的 outcome 没有送入执行器；连续 3 次稳定复现，仅留下前三类证据。复现断言故意为红：`Late original-call completion was dropped after stopping the execution`。
4. 这只证明 Rust 接收侧存在取消收尾缺口，不能替代真实 Worker → Rust → 持久化的端到端证明，也不能独自确定历史进程只经过这一条路径。真实 Worker 的模型证据 RPC 与生成使用同一取消信号，`cancel()` 又拒绝全部 pendingTools；Rust 每次转交工具 RPC 前还会刷新业务输出。延迟 Rust 注销本身不足以修复完整链路，历史原始调用状态继续保留。
5. 另外 4 个 BYOK 旧执行均在 2026-10-15 收到 HTTP 503，最后调用 outcome_unknown、没有最终用量，执行 awaiting_reconciliation。当前对已发送且结果不明的调用禁止自动重发，是为避免重复上游请求。补 Key 不能解决这类未知调用，但界面仍统一提供恢复入口。
6. Worker 已区分 authentication/rate_limited 等错误；执行后端除上下文错误外大多重新写为 generation_failed，公开接口又只保留少量错误码，用户看不到可操作的原因。
7. BYOK 连接信息与上下文/模型能力存在两个前端状态来源；上下文在表单外即时保存，连接参数需另外点击保存。输出上限和推理协议已有发送字段，但当前模型配置界面未提供相应完整编辑入口。

## 选择与推荐

- 推荐一次覆盖直接链路：修复证据收尾，明确恢复能力与错误码，统一 BYOK 配置和费用说明。复用原执行器，不另建一套 BYOK Agent 循环。
- 可分阶段先只修取消收尾，再单独处理配置和状态界面；改动更小，但 503 时无效恢复提示等体验问题仍需下一轮处理。

## 拟实施范围

### A. 停止后只收尾原调用的证据

**生命周期分为生成、证据收尾、关闭三段。** 停止事务提交后，执行立即成为 stopped；生成取消、证据收尾和资源释放必须独立处理，不能只延迟 Rust 注销。

1. **真实 Worker 的两个取消域。** `execution_message` 的模型生成、业务工具、审批、prepared/dispatched、checkpoint 和普通流事件使用生成取消信号；已经登记的原调用的 usage/receipt/outcome 使用独立证据取消信号与 pendingEvidence 集合。收到取消时，立即中止生成并拒绝业务工具/审批，但保留证据 RPC 等待真实持久化 ACK。`receiveToolResult` 对两个集合按真实请求 ID 路由，不伪造成功。只有模型取消清理完成且证据已确认，或收尾预算耗尽后，才发送该请求的最终协议终止事件并清理接收；不能因为生成 Promise 先结束就清掉 pendingEvidence。普通非执行请求保持原取消语义。
2. **证据权限受限。** Worker 和 Rust 都只允许此前已经登记的原账号、execution、call、fence 的三类证据。收尾模式禁止 prepared/dispatched、新模型请求、工具恢复、业务工具、审批、上下文资料写入和 checkpoint。消息类型、原调用身份和既有大小限制仍须验证，不能仅凭 `__model_call_observation` 名称放行任意内容。
3. **绕过业务输出。** Rust 在正常运行和收尾时均先识别允许的原调用三类证据，直接交给专用、可独立持有的持久化接口；这些事实始终不依赖 `on_flush`、业务事件或最终答案回调，也不复用通用工具执行分派。这样即使数据库已停止、本地取消信号尚未观察到，缓存文本的旧 fence 写入失败也不能挡住证据。进入收尾后停止全部输出回调，原有缓存文本直接放弃，不向新 fence 再写。Worker 的证据提交同样不依赖已停止的业务 checkpoint；原始依据持久化之后，其 ACK 不因后续 checkpoint 失败而被误判为未保存。
4. **迟到记录仅归原执行。** 停止后继续拒绝旧回复、地图和画布写入；不能把 Token 数、单帧用量或部分工具片段改成执行成功。可信 outcome 可补到原调用，执行仍为 stopped，原始依据与管理员证据版本规则保留。共享桥接中的现金/积分也只获得相同的依据收尾保护，计费规则不变。

### A1. 收尾的资源、时限与 ACK 约束

- **固定截止时间。** 本进程显式停止事务成功返回后立即记录单调时钟 `t_stop`，在发取消通知和任务移交之前建立至多 `t_stop + 5 秒` 的截止时间；重复停止、收到更多证据、RPC 重试或等待资源均不延长。另一实例停止时，使用既有停止事件的数据库时间与同次读取的数据库当前时间换算剩余预算，首次观察已超过 5 秒就不再打开窗口；租约丢失而尚无 stopped 事件时，按首次失去所有权时刻建立一次最多 5 秒的审计收尾。Rust 截止时间是最终接收边界，Worker 只能使用剩余预算，不能再另等一个完整 5 秒。
- **内部取消契约。** 内部 `cancel` 帧增加可选的 `evidenceDrainMs`，由 Rust 按当前剩余预算生成，合法范围为 0～5000；重复 cancel 只能缩短，不能延长 Worker 的原截止时间。已关闭请求的重复 cancel 不得重建请求或使共享 Worker 退出。新 Worker 未收到该字段时沿用旧的立即取消语义；旧 Worker 会忽略该可选字段并按原语义取消，新 Rust 只能保留未知结果，不能把缺失 ACK 当成功。配套 Worker 与 Rust 一起发布，并验证这两种内部版本组合。
- **先释放生成资源。** 在把请求移交证据收尾时，释放生成 semaphore permit、生成 active 注册、续租心跳和业务回调持有关系；后续 `run_owned` 的终止不能再次释放新执行的资源。收尾不得持有生成名额、会话/钱包锁或数据库事务，也不得继续引用可以写业务输出的回调。新请求遵守原有队列和资金规则，但不等待旧请求收尾结束。
- **独立且有界。** 只为已有待确认模型调用或证据的请求分配收尾，纯排队/无调用的停止直接结束。每个应用进程最多同时处理 2 个原请求的收尾；Worker 也限制为最多 2 个收尾请求。每个收尾请求最多 32 个尚未 ACK 的证据 RPC，沿用既有消息字节限制。收尾使用非阻塞的名额获取，不建立等待队列；没有名额或预算已耗尽时立即关闭该请求的收尾并保留已持久化依据及未知状态，不能占住生成名额等候。受控关闭同样服从剩余预算，不无限等待证据 Promise。
- **已发送但未 ACK。** 取消生成时不批量拒绝 pendingEvidence；窗口内继续接收真实持久化 ACK。重放只能沿用原调用与证据摘要去重；DB/日志已成功但 ACK 丢失时，不新增金额、不生成新模型调用。到期后拒绝并清理全部尚未确认的证据 Promise、定时器与请求注册，不能返回虚假的成功 ACK。
- **超时之后。** 已持久化的数据保持原样；仍无可信 outcome 的调用保留 dispatched/outcome_unknown，记录封闭的收尾超时/容量原因供审计。已登记的迟到 ACK 不得导致共享 Worker 退出或影响新请求；关闭请求标记最多保留 256 项，同一请求只记录一条封闭的收尾诊断，不保留完整 ACK 内容。超出登记范围的无主 ACK 也只能丢弃并记有界诊断，不能重建旧请求、恢复生成或被当成完成依据。重启仅重放已持久化的原始日志，不自动重发未知调用。

### A2. 必须使用真实协议的收尾验收

- 保留自写 Worker 复现作为 Rust 单点回归，并明确其覆盖限制。
- 决定是否通过的集成测试使用真实 Worker 进程、`ProtocolServer`、`HarnessRunner`、Rust 运行桥接、原始 journal 和独立 PostgreSQL 数据库。fixture 只控制上游模型流、错误和时序，不替换取消处理、host RPC、ACK 或持久化实现；不修改生产 DNS/权限限制来迁就测试。
- 覆盖取消前证据已发但未收到 ACK、取消后原调用产生证据、checkpoint 因停止失效、Rust 仍有缓存文本且刷新会失败、数据库已 stopped 而本地尚未观察到取消、持久化成功但 ACK 丢失、5 秒到期、证据容量耗尽。验证原证据确实入库且可重放去重，停止后的回复/地图/画布没有写入。
- 单生成名额测试中，旧请求证据 ACK 被 barrier 暂时扣住时，新请求仍能取得唯一生成名额；连续停止验证收尾并发始终不超过 2、没有排队积压、计时不会重置、到期清空 pendingEvidence，迟到 ACK 不破坏新执行或共享 Worker。

### B. 分开恢复条件、执行异常和费用状态

- 公开控制信息使用封闭原因码和操作能力，至少区分缺原 Key、上游调用结果未知、可继续恢复、已经终止；只暴露必要状态，保留私有上游响应和凭据的隔离。不能直接向既有 `AgentStatus` 追加字段，具体兼容契约见 B1。
- 继续使用现有执行/结算状态枚举，在既有 JSON 原因和 API 投影中表达细分状态；此方案无需新增数据库迁移。
- 只有缺原 Key 且其余条件满足时提供“补充原 Key → 恢复”。BYOK 的 503/断流等不可恢复未知调用结束本轮为 failed，保留原调用未知依据与仅审计记录，不等待管理员核账来解锁。旧的等待记录只在用户明确结束原请求时停止，不批量改写；现金/积分原保护保持。
- 绝不将未知的原调用自动重发，绝不因改配置就改变已经接受执行的模型/Key 绑定。显式新发使用新的操作标识，提示原上游调用费用仍由服务商决定。
- BYOK 成功显示“使用自带 Key，未扣本站额度”；异常按执行和原始调用依据解释，不把缺人民币回执本身作为 BYOK 财务故障。现金、积分缺证据的保护继续保留。
- 保留已发布的管理员重核/归档、证据指纹和迟到证据重开规则；不自动处理历史生产记录。

### B1. 保留旧响应，新增独立控制查询

- **既有响应保持原契约。** 接受、查询、当前活动执行、停止、恢复和全局助手快照内嵌的状态继续只返回原 7 个顶层字段：executionId、conversationId、state、funding、modelId、result、error。既有错误投影和 SSE/完成结果结构保持兼容，不在这些对象中追加 reason/actions，也不把旧客户端的严格解析器改松来代替兼容。
- **新接口。** 新前端额外调用只读 `GET /api/me/agent-executions/:executionId/control`，返回独立的 `version: 1`、executionId、conversationId、state、reason 和 actions；其字段和枚举在独立类型中严格验证。reason 是封闭分类，actions 包含 canCheck、canStop、canResume、needsCredential；不提供上游原始响应或密钥。使用现有账号、未删除会话及绑定规则授权，响应禁止缓存。
- **竞态保护。** 控制信息与当时执行/调用状态按一致快照读取，只作为操作提示。前端绑定账号、execution 和读取轮次，丢弃迟到或已被新终态覆盖的控制响应；停止/恢复入口仍在既有事务锁内重新检查真实状态及原 Key/调用，不信任客户端 action 布尔值。
- **新前端访问旧后端。** 先有成功读取的旧状态，再发现 control 不受支持时，采用保守降级：保持查询、停止和合法终态后的新发送；只有旧错误明确为 credential_required 才展示补原 Key 的恢复路径。未知结果不推断为可恢复，不自动重试或切换资金通路。401/403、执行已删除、网络错误、HTML 或无效响应不能被当作接口不受支持而放开操作。
- **组合验收。** 固定旧前端解析器/构建验证旧前端+旧后端、旧前端+新后端、新前端+旧后端、新前端+新后端四种组合；覆盖接受、查询、停止、恢复、活动执行、全局快照及事件完成。旧标签页不刷新也能继续解析原响应，新客户端降级不显示不可能成功的恢复操作。

### C. 统一错误与配置

- 保留认证失败、限流、余额不足、网络失败、上下文不足和调用结果未知等封闭原因，贯穿 Worker → Rust → 数据库 → API → 前端；不把上游私有 body 或 Key 放入公开错误。
- 把 Key、URL、模型、上下文、可选输出上限与推理协议作为一份前端 BYOK 草稿一起校验和应用；学习区、酒馆、全局助手共用。默认遵循已有能力声明，不按模型名称猜测支持情况。
- Key 仍限当前页面/服务进程内存，不写 localStorage、数据库或日志。刷新/重启后需要原 Key 时给出准确说明。
- “测试连接”明确只验证模型目录访问，不能冒充聊天/工具调用兼容性验收。

## 用户确认后的补充：本站额度与 BYOK 隔离

- 本站现金为负或零，不能拦截使用有效自带 Key 的接受、执行或显式新请求；上游自带账户欠费另按 provider_balance_insufficient 解释。
- 先验证后端现金门槛只在 funding=cash 生效，再复现“现金发送明确被拒绝 → 用户切换 BYOK → 再发送”的前端流程。已明确拒绝且未接受的现金操作不能被当成结果未知长期保留；保留输入，下一次明确发送使用当前资金通路和新操作 ID。
- 已接受或接受结果仍未知的请求继续绑定原资金/模型，不能因切换配置而偷换原请求；丢响应必须沿用原 ID 读取或核对，不能直接改发另一通路。
- 回归接口沿用已确认的前端真实页面/公共运行控制器与 HTTP、后端 service/store/HTTP 和 Worker 协议/持久化边界；覆盖独立酒馆、学习区、全局助手与现金保护。
