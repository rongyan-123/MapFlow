# 消息全部已读与单条操作稳定性

2026-10-21 用户确认范围：消息中心增加全部已读，公告页提供仅公告的全部已读，修复单条确认时的布局变化与快速连点，并继续核对偶发连带确认。复用当前会话前后端工作区；先完成本地验收。

## 产品行为

- 消息中心底部常驻“全部已读”，不需要打开每条详情或翻完所有页。处理当前账号已有公告和反馈回复，不受当前分类影响。
- 全部公告页提供同名按钮，只处理公告。没有未读或正在提交时禁用；失败保留真实未读状态，可再次点击重试。
- 单条确认只提交目标 ID，成功后按钮在原位置显示禁用的“已读”。两个入口的已读状态和铃铛同时刷新。
- 同一目标的进行中请求去重；单条和全部仍是不同函数与接口，不因复用误清其他消息。
- 米色与暗色沿用现有按钮样式；底部操作在窄屏、桌面与横屏可见，触控高度至少 44px。

## 数据与并发

新增 `/api/me/notifications/read-all`，kind 为 all、announcement、feedback_reply。沿用账号登录和防跨站请求校验。服务端同一数据库语句处理公告及反馈，重复操作无额外已读记录；语句开始后新来的消息保持未读，失败整体回滚。

旧单条接口及列表响应保留，不修改聊天、模型、计费、通知内容或公告发布逻辑，不需要数据库迁移。前后端需一起发布才能使用新增按钮；新后端仍支持旧页面。

## 诊断边界

本地六条公告场景确认：原界面成功后移除按钮，下一条公告上移约 61–62px；快速连点可在禁用状态渲染前重复提交相同目标。另有消息中心单条已读未刷新旧公告缓存的问题，已通过失败测试确认。

没有复现一次单击提交两个不同公告 ID，不能据此宣称已证明用户原始偶发现象的完整根因。本轮按证据修复位移、重复请求和缓存同步；继续用实际请求目标核对，不依赖按钮消失判断成功。

## 步骤与验证

1. 后端 HTTP 测试先红后绿：超过一页、账号与权限隔离、分类、重复请求；以真实行锁协调验证新消息边界，注入失败验证整体回滚。
2. 前端组件测试先红后绿：全读入口、固定单条控件、连点去重、两个入口缓存同步；补充失败重试与操作期间新消息。
3. 完整测试、类型检查、格式／静态检查与构建；区分既有 Windows 环境差异。
