# MapFlow 请求生命周期矩阵改版设计

日期：2026-08-31
状态：用户已批准设计，等待书面规范复核

本文件是 `2026-08-31-request-observability-design.md` 的改版补充，并覆盖其中“固定生命周期模型”“管理 API”“管理界面”“测试策略”和相关验收标准；原设计中的安全、保留、异步写入和回滚约束继续有效。

## 1. 背景与问题

现有“请求观测”功能已经能持久化固定 11 阶段生命周期，并在详情抽屉中展示完整阶段、解释和脱敏技术诊断。但当前列表只返回请求摘要，主表无法直接展示阶段；“停止阶段”筛选又容易被误解成“经过阶段”筛选。

生产数据和现有代码确认了四个具体问题：

1. 列表行的数据契约不含阶段状态，完整路线只能再请求详情接口。
2. 详情抽屉最大宽度约 1152px，现有 11 个固定宽度节点合计至少约 1784px，右侧节点只能通过横向滚动看到。
3. 成功请求没有异常终止阶段，现有默认选中逻辑会退回第一个客户端节点，而不是最后的 HTTP 响应。
4. 用户名位于主表靠右位置；窄视口下整列被横向溢出隐藏。用户名为空时又统一显示“未识别用户”，混淆了访客、身份失败和真正无法关联账号三种情况。

此外，当前采集并不能证明每个业务接口是否真正经过业务服务或 PostgreSQL。未显式埋点的阶段不能被展示成确定的“未经过”。

## 2. 目标

改版后的默认主视图必须让管理员无需筛选、无需打开详情、无需水平滚动，就能回答：

- 这是谁的请求，或为什么没有用户名。
- 请求 ID、IP、方法和规范化路由是什么。
- 请求按固定架构顺序经过了哪些阶段。
- 哪一层拒绝、失败、等待或缺少采集证据。
- 请求最终落到哪里、返回什么 HTTP 状态、耗时多久。

详情视图继续承担教学解释和技术排障，但完整路线的末端必须在打开时立即可见。

## 3. 方案选择

### 方案 A：视口内生命周期矩阵（采用）

主表左侧固定请求身份，中间用 11 个紧凑阶段列组成矩阵，右侧固定最终结果。详情使用自适应等宽时间线，桌面端一屏展示全部节点，窄屏改为纵向。

优点：符合“从左到右”的学习心智模型；可以横向比较多条请求；终点始终可见。缺点：阶段标题需要短标签、完整标题和解释需要通过悬停或详情展示。

### 方案 B：保留大节点并自动滚到终点（不采用）

改动较小，但打开后仍无法同时观察完整路线；中间阶段仍被滚动区域隐藏，不满足学习目标。

### 方案 C：两行折返时间线（不采用）

可以保留较宽节点，但路线方向会在换行处改变，降低从入口到响应的线性直觉，也不利于逐行比较多条请求。

## 4. 固定生命周期与显示语义

主表和详情始终按以下顺序展示全部阶段：

1. 客户端
2. Caddy
3. 路由
4. 安全
5. 身份
6. HTTP
7. 业务
8. PG
9. Worker
10. 外部
11. 响应

紧凑单元格使用图标、短文本和颜色共同表达，不允许只靠颜色：

| 状态 | 紧凑显示 | 含义 |
| --- | --- | --- |
| `passed` | `✓ 有` | 有直接测量或可信代理证据证明已经过 |
| `rejected` | `× 拒` | 该阶段主动拒绝请求 |
| `failed` | `! 错` | 该阶段出现非预期异常 |
| `pending` | `↻ 待` | 已交给异步工作，尚未完成 |
| `not_reached` | `— 无` | 拓扑明确且有证据表明请求在更早阶段停止 |
| `not_applicable` | `∅ N/A` | 本类路由按设计不需要该阶段 |
| `unobserved` | `? 未采集` | 当前埋点无法证明经过或未经过 |

`unobserved` 是本次改版新增的真实语义。系统不得把没有采集证据的阶段自动绘制成“已通过”或“未经过”。旧记录在无法可靠转换时按“未采集”展示。

生命周期 schema 版本由 v1 升至 v2。v2 新记录必须原生保存 `unobserved`；读取 v1 记录时，仅当路由拓扑和更早的明确终止证据足以证明时，才把旧 `not_reached` 保留为“未经过”，其余旧 `not_reached` 转换为“未采集”。

## 5. 主表设计

主表采用三段式布局：

### 左侧固定身份区

- 用户名或身份状态。
- 有效客户端 IP。
- 短请求 ID，支持复制完整 ID。
- 完成时间、HTTP 方法和规范化路由。

身份显示规则：

1. `username` 存在：显示用户名，可在次级文字中显示账号 ID。
2. 身份阶段为 `not_applicable`：显示“访客（该接口无需登录）”。
3. 身份阶段为 `rejected`：显示“未登录 / 身份校验失败”。
4. 其他没有账号信息的情况：显示“未能关联账号”，并明确这属于采集或上下文缺失。

后端列表摘要返回稳定的 `actorKind`：`authenticated`、`visitor`、`identity_rejected` 或 `unassociated`。前端只负责翻译显示，不自行从多个阶段重复推断身份类型。

左侧身份区必须保持可见，不得把用户名放到需要横向滚动才能看见的位置。

### 中间生命周期矩阵

- 11 个阶段列固定顺序、固定短标题。
- 每个单元格直接显示本次请求的阶段状态。
- 悬停或键盘聚焦显示完整阶段名称、证据类型、耗时和一句人话解释。
- 点击任一单元格打开详情，并自动选中对应阶段。
- 不依赖任何筛选器才显示阶段。

### 右侧固定结果区

- 最终落点。
- HTTP 状态码。
- 总耗时。
- 请求结果：成功、拒绝、异常或异步处理中。

最终落点规则：

- 成功或重定向：HTTP 响应。
- 拒绝或失败：最后一个明确为 `rejected` 或 `failed` 的阶段。
- 异步处理中：最后一个明确为 `pending` 的阶段。
- 证据不足：显示“终点未采集”，不能猜测。

## 6. 筛选器调整

筛选器保留为排障辅助，不再成为理解请求路线的前提。

- “结果”和常用搜索保留在紧凑工具栏。
- 其他条件折叠进“高级筛选”。
- “停止阶段”改名为“拒绝 / 异常发生层”，并只筛选真正以该层为拒绝或失败终点的请求。
- PostgreSQL、业务服务、HTTP 等主阶段是否经过，直接看矩阵单元格，不通过终止阶段筛选推断。

## 7. 详情抽屉

详情顶部先显示明确结论，例如：

- “正常完成 → HTTP 响应 200”
- “安全守卫拒绝 → HTTP 429”
- “外部模型调用异常 → HTTP 502”

桌面端时间线使用 11 列自适应等宽网格，不再使用 144px 固定节点和横向滚动。节点使用短标题，完整标题在选中检查器中展示。窄屏端改为从上到下的纵向时间线。

默认选中规则：

1. 拒绝或失败请求选中实际终止阶段。
2. 异步请求选中等待阶段。
3. 成功请求选中 HTTP 响应。
4. 如果终点证据不足，选中最后一个有明确证据的阶段。

运行位置泳道、人话解释、证据类型、阶段耗时、脱敏技术诊断和完整脱敏 JSON 继续保留。

## 8. 管理 API 与数据流

列表接口在每条摘要中新增轻量生命周期数据，包含固定 11 个阶段的：

- `id`
- `status`
- `evidence`
- `durationMs`

悬停提示使用阶段 ID、状态、证据和耗时生成固定说明；完整人话解释只由详情接口返回。这样列表契约保持轻量且没有两套可漂移的解释文本。

列表接口不返回阶段的完整 `technical` JSON，避免一次分页加载 50 份大诊断。详情接口继续返回完整脱敏阶段数据。

PostgreSQL 列表查询直接读取同一行已有的 JSONB 阶段快照并生成轻量摘要，不允许前端对 50 行逐条请求详情，也不允许后端产生 N+1 查询。

列表解析必须验证：

- 恰好包含 11 个阶段。
- 阶段顺序与 schema 版本一致。
- `passed` 只能使用 `measured` 或 `confirmed_header` 证据。
- 未知或旧 schema 不伪装成绿色通过。

## 9. 采集真实性改进

为每个当前生产路由族补充预期拓扑模板，覆盖：通用能力接口、身份、邀请码、管理、公告、积分、公共树、个人库、树生成和知识聊天。

每份模板明确：

- 哪些阶段按设计不适用。
- 哪些阶段理论上可能经过但当前尚未埋点。
- 哪些阶段只有直接测量后才能标记为通过。

对当前生产路由补齐业务服务和数据库边界的显式埋点。共享身份会话查询造成的数据库访问，与业务处理自身的数据库访问可以共享一个阶段状态，但详情必须分别列出已测量到的操作来源，避免把“读取会话”误解成“业务数据已查询”。

同一请求重复经过同一阶段时，阶段对象保存一个有界的操作摘要列表，而不是忽略第二次通过或覆盖第一次证据。每项包含稳定操作码、开始偏移、耗时和脱敏说明；最多保存 16 项，超过后设置截断标记。阶段总状态按最严重结果聚合，列表矩阵仍只显示一个紧凑状态，详情检查器展示各次操作。

本次不引入外部可观测性服务，也不记录请求体、密码、Cookie、Authorization、CSRF、API Key、邀请码或用户聊天内容。

## 10. 错误与兼容处理

- 旧记录缺少新增状态时，客户端或后端适配层将不能证明的阶段显示为“未采集”。
- 列表生命周期数据损坏时，该行显示“生命周期数据异常”，但不打挂整个管理标签页。
- 详情接口失败时仍保留列表矩阵和请求 ID，允许管理员复制 ID 排查。
- 观测写入失败仍不得影响业务请求。

## 11. TDD 与验证

实施必须先写失败测试，再写实现。

### 后端

- 列表摘要包含固定 11 阶段轻量数据。
- 列表查询单次完成，无逐行详情查询。
- `unobserved`、`not_reached` 与 `not_applicable` 不混淆。
- 路由拓扑模板和关键路由业务/数据库埋点符合真实路径。
- 已登录请求保留用户名；公开请求和身份失败能够正确分类。
- 旧记录和损坏阶段数据安全降级。

### 前端

- 主表无需打开详情即可看到 11 个固定阶段。
- 用户名或身份状态位于固定可见区。
- 成功请求默认选中 HTTP 响应；拒绝和失败请求选中真实终点。
- 桌面详情时间线不使用横向滚动，并渲染全部 11 个节点。
- 每种阶段状态都有文字、图标和可访问名称。
- 点击主表阶段单元格能打开并选中对应详情节点。
- 筛选器改名后不会再把“经过阶段”和“异常发生层”混淆。

### 完成前

- 后端完整测试、格式检查和 Clippy 通过。
- 前端组件测试、客户端契约测试、TypeScript 类型检查和生产构建通过。
- 重跑原始复现检查：用户名在可视区；生命周期末端无需横向滚动；列表契约携带阶段。
- 生产冒烟确认管理接口、普通业务请求和服务器资源占用正常。

## 12. 实施边界与上线

实施跨越前端和后端两个现有仓库，只修改请求观测相关代码和必要的路由埋点，不重构无关业务。

上线顺序：

1. 部署向后兼容的后端列表契约与采集改进。
2. 验证新旧记录均可读取。
3. 部署前端矩阵界面。
4. 运行生产冒烟和资源检查。

如果前端需要回滚，后端新增轻量字段可以继续保留；如果后端需要回滚，前端必须识别旧契约并显示独立错误，不得伪造阶段结果。

## 13. 验收标准

- 管理员打开请求观测标签页时，不使用筛选、不点详情即可看到每行完整 11 阶段。
- 用户名或准确的无用户名原因无需横向滚动即可见。
- 成功、拒绝、失败和异步请求的最终落点无需横向滚动即可见。
- PostgreSQL、业务服务和 HTTP 不再通过“停止阶段”筛选表达是否经过。
- 所有不确定采集都显示“未采集”，没有无证据的绿色通过或确定未经过。
- 点击任一阶段仍可查看人话解释、证据、耗时和脱敏原始诊断。
- 列表加载不产生 N+1 请求或查询。
- 业务流量、服务器稳定性和观测数据安全边界不因改版退化。
