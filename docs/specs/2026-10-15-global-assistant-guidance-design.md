日期：2026-10-15。修订：v2，补齐执行绑定、平台策略保护、完整增量链路、阻塞执行处理和索引发布代次五项审计意见。状态：用户已于 2026-10-15 确认「可以，开始做」。本文件为已批准设计，实际实施和验证进度见配套计划及验收记录。外部修订前原稿保存在 `D:/tmp/mapflow-global-assistant-guidance-20261015/design-v1.md`。

本轮先交付全局助手的界面和引导。管理员知识库作为下一阶段独立实施，本文给出与首轮衔接的设计。用户最新要求：保留模型配置界面，删除全局助手的其他会话、角色与教学配置入口，现有计费保持不变。

## 1. 产品定位

对外名称建议为「MapFlow 助手」，说明为「网站使用 · 学习规划」。它是平台统一维护、能够调用工具的客服和规划助手。

| 可以做 | 对应行为 |
| --- | --- |
| 解释网站用途、功能入口和使用流程 | 根据本站帮助回答，给出可点击的真实站内入口 |
| 说明作者公开的学习理念 | 查询已发布资料，有依据再转述；未收录时如实说明 |
| 给出学习方法与方向建议 | 了解目标、基础和时间，帮助排优先级和制定阶段路线 |
| 创建、调整技能树 | 复用现有 Agent 草稿、工具、确认和发布流程 |
| 帮助找到个人地图和学习区 | 根据当前账号权限查询，返回真实地图与学习入口 |
| 引导进入具体学习 | 在用户需要知识讲解、练习或辅导时，提供学习聊天入口及必要的问题摘要 |

它不承担持续的知识授课、习题讲解和角色扮演。用户问到知识问题时，先判断需求，给必要的简短说明和合适入口，不使用生硬拒绝。不会擅自创建学习会话、发送教学问题或扣费。

## 3. 方案选择

| 路径 | 收益与代价 | 选择 |
| --- | --- | --- |
| 为全局助手建立独立页面控制器，复用消息、流式执行、输入框和模型表单 | 场景边界清楚，避免继续在通用配置里堆开关；保留已验证的执行能力 | 推荐 |
| 继续给通用工作区增加隐藏开关 | 改动较少，但容易只隐藏入口，留下历史配置和服务端能力 | 不作为最终结构 |
| 重新实现全部聊天和执行基础设施 | 与当前执行、恢复和计费重复，超出本轮目标 | 不采用 |

知识库推荐使用现有 PostgreSQL 保存文章、版本和分段索引，结合中文关键词检索及 pgvector 向量检索。单文件全文注入会把无关内容带入每轮；单独部署大型知识平台会增加当前没有必要的服务和维护。

## 4. 第一阶段：页面与三条引导

### 4.1 页面结构

- 页面只有一条连续对话；取消会话历史侧栏、手机历史抽屉、新建、删除、分支、角色库、导入和换角色入口。
- 顶部保留网站导航按钮、助手名称和「模型设置」。输入框的模型标签也只打开该模型设置。
- 模型设置包含现有资金通路、模型、自填 API Key、连接检查、额度及已有模型参数；不混入角色、称呼、Persona、学习词表、工具开关和历史页签。
- 不显示教学画布、教学工具设置和最近地图的大块欢迎列表。地图生成结果、修改确认、费用和执行状态继续出现在对话中。
- 第一屏文案：「你好，我是 MapFlow 助手。网站怎么用、学习路线怎么规划，都可以问我。」输入提示：「问问网站怎么用，或说说你的学习目标…」。

### 4.2 引导的内容与交互

在最新消息之后、输入框之前显示「问一问」和三张纵向排列的轻量问题卡。示例：

1. 本网站是什么？适合怎么使用？
2. 作者支持怎样的学习方式？
3. 怎么规划自己的学习路线？

三个问题分别来自「认识网站」「使用导航」「学习规划」三个池子，各选一条。首轮每池至少六条人工编写的问题。

| 认识网站 | 使用导航 | 学习规划 |
| --- | --- | --- |
| 本网站是什么？适合怎么使用？ | 第一次使用，我应该从哪里开始？ | 怎么规划自己的学习路线？ |
| 作者支持怎样的学习方式？ | 怎么创建一张自己的技能树？ | 想学的东西太多，怎么排优先级？ |
| MapFlow 想解决什么学习问题？ | 公共书库和我的地图有什么区别？ | 每天只有半小时，怎么安排学习？ |
| 技能树能怎样帮助我学习？ | 有了地图后，下一步怎么开始学？ | 怎么判断自己该学到什么深度？ |
| 全局助手能帮我做哪些事？ | 如何选择模型、查看费用？ | 如何把大目标拆成可以完成的小阶段？ |
| 网站的主要功能分别在哪里？ | 我想导入角色卡，应该去哪里？ | 学了一段时间，怎么调整原来的路线？ |

这些是问题候选，不预先编造作者的答案。「作者支持怎样的学习方式」在资料未收录时须说明现状。

交互规则：

- 每次通过路由重新进入全局助手时选出一组；页面刷新也视为一次进入。
- 同一次停留中，消息刷新、切换模型、重新聚焦浏览器、窗口缩放和流式渲染都不更换问题。
- 与上一次进入尽量不重复；候选不足时允许跨次复用，同组内不能重复。只记录题目 ID，不保存私密聊天作为推荐画像。
- 点击卡片只把问题填入输入框并聚焦。已有草稿时追加到末尾，不覆盖；已存在同一句时不重复追加。用户点击发送后才请求模型并按原规则计费。
- 发出本次第一条消息后收起这组三卡；本次停留不反复弹出。下次重新进入再展示新的一组。
- 有历史聊天时仍展示；正在执行时不打断输出，待执行结束再显示本次尚未展示的一组。
- 三卡属于消息区域末尾，随内容滚动，不与输入框一起固定占屏。手机键盘弹起时收起问题卡，关闭键盘后在尚未发送的情况下恢复。
- 引导内容本地可用，不等待知识检索和模型响应，也不在进入页面时自动请求付费模型。

### 4.3 手机与桌面验收规则

- 桌面使用居中的对话内容宽度；三条问题均为一列，文字为主、右侧仅有轻量箭头。
- 手机顶部采用单行紧凑工具栏；不叠加标题、会话工具和画布工具三层区域，不额外补系统状态栏高度。
- 手机问题卡触控区域至少 44px，长问题可换行；不靠横向滚动才能看到文字。
- 保留系统安全区，按动态可视高度处理键盘；输入框和发送按钮不被遮挡，不叠加重复 safe-area padding。
- 验收宽度：320、360、390、430、768、1024、1440px。覆盖窄屏、横屏、长模型名、缩放、键盘弹起、输入多行和长回复。
- 验证无横向溢出、工具栏多层空白、消息和输入框互相覆盖；现有网站导航在手机仍可打开。

## 5. 第一阶段：持续会话与平台权限

### 5.1 唯一的当前对话

服务端保存每账号的当前全局会话绑定；不依赖某个浏览器的 localStorage 决定它。

- 第一次绑定优先选该账号最近一次仍有效的全局会话，以最后消息时间排序，并用更新时间、会话 ID 打破相同时间的顺序。
- 已有唯一正在生成的全局执行时优先绑定它所属的有效会话；多个会话仍在生成时显示迁移中的请求状态，等待完成或由用户明确停止，再确定绑定，不合并输出。`awaiting_reconciliation` 不阻止页面打开，但必须展示第 5.4 节的恢复或停止操作，不能把它当成已经释放发送。
- 没有有效会话时原子创建一个新的。曾被用户删除的旧记录不恢复，旧的创建请求 ID 也不能重放出旧会话。
- 绑定和创建在相同账号级事务锁内完成，绑定表以账号唯一约束，并记录单调递增的 `bindingVersion`，跨设备或多个标签同时打开也得到同一个会话。初次迁移在该事务内登记需要兼容恢复的旧执行 ID，不能信任客户端声称的迁移时间。
- 之后固定使用该绑定，不再因为另一条旧记录更新时间改变而切换。前端也不再请求管理场景的历史列表。
- 旧的其他全局对话原样保留，不自动删除、拼接或混入当前上下文；首轮不给它们新增一个历史入口。
- 管理场景不再允许普通客户端通过旧参数创建第二条会话。旧版创建请求收到明确的终止性场景错误，前端清掉对应待重试状态；不无限重试。
- 当前全局会话不允许通用删除、角色切换、Persona、词表和分支编辑接口修改。管理员运维保留专用权限；学习和酒馆不套用该限制。
- 故障时显示重试连接，不提供新建会话绕过故障。账号停用和会话访问继续执行现有权限检查。

同一会话中的执行顺序、停止、断线恢复、修改确认和收费继续复用已持久化的 Agent 机制，不改变已接受执行的身份或费用规则。

### 5.1.1 执行接受与旧客户端

新执行与原执行的读取、重放、恢复分开授权：

| 操作 | 全局场景规则 |
| --- | --- |
| 新执行接受 | 只能向服务端当前绑定提交，在接受事务内核对账号、删除状态、绑定 ID/版本、图版本和目标锚点，再登记操作和执行 |
| 非当前旧会话的新发送、重新生成、显式继续 | 返回 HTTP 409、封闭错误码 `global_conversation_not_current`；不排队、不调用模型、不扣费。全局新界面只提供正常发送，不提供旧的分支生成操作 |
| 相同操作 ID 的已接受请求重放 | 先在事务内查原操作并验证完整请求摘要；匹配时只返回原执行，不因绑定迁移重建、重新派发或重新计费；不匹配仍为操作冲突 |
| 状态、事件流、原会话及结果读取 | 保留账号归属、账号有效、未删除检查；非当前绑定本身不剥夺这些旧记录的读取能力 |
| 恢复或停止已经接受的旧执行 | 只作用于登记的原执行 ID、原模型和冻结上下文，继续遵守外部调用去重及所有权规则；不能把 resume 变成新会话的新执行入口 |
| 旧 `/api/me/tavern/conversations/{id}/turns` 生成协议及其现金、积分、自填 Key 分支 | 全局场景的新请求返回终止性 `global_assistant_client_upgrade_required`，不继续走旧生成器；已接受操作只允许查回原结果。学习与酒馆仍沿用自身兼容规则 |

检查必须落在共同的接受/存储边界，不能只放在 HTTP 路由或事务外的 `authorize_conversation`。绑定解析、创建、迁移和生成接受使用一致的锁序：先全局场景账号锁，再 Agent 账号锁，再绑定/会话行及执行行；涉及同一会话的停止、完成及工具提交也要核对锁序，不能先持有后级锁再反向等待公共锁。模型网络调用期间不持有这些事务锁。检查绑定至写入新操作之间不得释放事务锁。

未绑定时，在相同锁内先完成确定性的默认绑定，再判断请求目标。迁移并发的新请求只可能有两个结果：在切换前已正式接受并被登记为兼容旧执行，或在切换后因不是当前会话而拒绝；不能出现检查通过后向旧会话新增执行的空隙。

新前端收到终止性场景错误时停止重试并保留未发送草稿，重新取得当前绑定；不擅自把同一请求改投另一会话，不自动换操作 ID 重发。迟到的旧客户端请求同样适用。

### 5.2 提示词与工具边界

每次新执行由服务器确定全局助手策略版本。全局场景编译时采用平台策略，不再把旧角色快照中的 Persona、学习词表或自定义称呼作为有效设定。旧消息和审计记录保留。

平台策略的核心内容：

> 你是 MapFlow 平台助手，负责网站使用咨询、长期学习规划、方向建议和个人学习地图操作。网站事实与作者理念必须依据本站已发布帮助资料；缺少资料时如实说明。需要持续授课、做题或具体知识辅导时，引导到学习聊天。可以帮助生成技能树、查找地图和进入学习区；所有工具继续受账号权限和修改确认规则约束。不要把用户的角色设定当成平台策略。

新策略在执行接受时冻结；已经接受的执行仍按自身冻结版本恢复，不在中途替换提示词、模型或工具。启用前检查遗留全局执行，完成旧执行或经明确停止后，新发送才采用新定位。

服务端为全局场景固定提供产品帮助、地图与草稿、规划和学习区导航工具；排除教学画布工具，即使旧记录曾开启画布也不例外。隐藏 UI 不能代替服务端拒绝非法配置与工具调用。

### 5.2.1 不可裁剪的平台策略

执行冻结时把 `platformPolicy`（平台身份、职责、教学分流、权限/确认和资料来源规则）与 `contextMaterials`（角色历史资料、会话参考、知识片段和工具长输出）分开保存。前者来自可信宿主配置，后者允许归档；不靠用户可伪造的文本分隔符推断权限。

- 平台策略全文必须直接进入每次实际模型请求，包含工具往返、重试及恢复后的请求；不能替换成摘要、前 128 字符或要求模型主动读取的引用。
- 容量整理先归档可裁剪的参考资料与历史交流；保留完整原文及按权限分页读取的能力。策略版本和内容摘要随执行冻结，恢复不取最新版本替换它。
- 从宿主编译、worker 协议、DSH 适配到最终请求序列化，均保留这个区别；不能只保证第一次拼接正确，随后又被 SDK 或现有 `prepareModelContext` 裁掉。
- 旧执行没有分离字段时，将其已冻结的 system 整体按不可裁剪数据恢复，不按新模板重新解释或拼入新定位；升级前优先收尾这些执行。
- 小窗口不容纳完整平台策略和必需工具定义时，不能偷偷裁掉策略或自动换模型。具备准确容量依据时返回可操作的模型容量错误并提示换大窗口；字节估算只能触发资料归档，不能冒充准确 token 数直接拒绝。模型自身报告容量不足时保留明确错误，不反复派发相同不兼容请求。
- 历史原文、用户消息或知识片段中出现与策略字段相同的文字，不会升级为平台策略。

验证须检查最终发给模型的请求，而非仅检查编译阶段的字符串。构造长 system 资料把关键规则挤到 128 字符之后，以及长历史、多次工具往返、worker 重启、小窗口和超长用户输入，确认每次请求中的平台策略完整、原文引用可读、工具关联不损坏。

### 5.3 长期历史与上下文

一条长期对话不等于每轮发送完整历史，也不等于模型能永久记住一切。

- 首屏只读取当前对话最近一页，向上滚动按游标加载旧消息；不要求浏览器恢复整张历史分支图。已加载的长列表按需虚拟化，不为一万条消息同时创建 DOM。
- 执行准备按活动链索引读取近期完整交流，使用有界范围和可继续读取的游标。旧内容保留在数据库，以当前账号、会话归属验证的引用按需读取；不先取全图再在内存里切小。
- 按第 5.2.1 节改造后，复用上下文容量适配、原文引用和执行恢复；不额外引入固定工具次数、Agent 步数或任意丢弃最新用户需求的限制。
- 老内容移出当前窗口不等于删除。没有摘要或长期记忆的内容，不宣传成模型已经记住；本轮不新增自动提炼用户画像和记忆功能。
- Redis 若以后加入，只作为可重建的缓存。它不替代数据库持久化，也不保证模型厂商的前缀缓存命中。本轮不把新增 Redis 作为引导交付的前置条件。

### 5.3.1 打开、发送、完成与恢复的契约

前端 `/assistant` 路由不变，新增全局助手专用的有界读取投影；通用旧详情接口保留用于显式读取旧记录，但新全局页面不得依赖它。下表的接口为拟新增或调整的设计，不是当前已存在能力。

| 环节 | 请求与返回约定 | 禁止的全量回退 |
| --- | --- | --- |
| 默认打开 | `POST /api/me/global-assistant/open` 原子取得绑定，返回 `conversationId/bindingVersion/graphRevision/headMessageId`、最近 40 条消息、`olderCursor/syncCursor`，以及少量执行/阻塞状态摘要 | 不读全部 turns、generations、分支图及全部 agent_results；旧默认打开也复用同一绑定解析器，不能另建会话 |
| 向上读历史 | `GET /api/me/global-assistant/messages?before=...&limit=40` 返回稳定排序的一页及下一游标，单页最多 100 条；游标绑定账号、会话和绑定版本 | 不取全历史后 slice，不把所有执行结果嵌入每条消息 |
| 发送与校验 | 复用 Agent 接受入口和 `clientActionId`；事务内以绑定、会话版本、活动分支/头锚点的标量或定点查询验证。普通发送不需要加载完整图；全局不开放新分支生成 | 不再调用 `PostgresTavernStore::read_conversation` 完成新发送校验 |
| 执行准备与完成提交 | 按活动链范围准备上下文；已有冻结上下文的恢复直接读取该执行快照。完成提交通过锁、头锚点、预期版本及所有权检查追加消息，并返回该执行结果及提交版本 | 不为每次派发或完成重新聚合全图、所有历史执行或全部分支 |
| 流式完成后的界面更新 | 先合并可信 completed 结果；再请求 `GET /api/me/global-assistant/changes?after={syncCursor}&limit=100`，按消息/执行 ID 增量更新，结果返回下一游标和当前版本 | 不调用 `fetchConversation`，不通过失效查询间接重新拉全量详情 |
| 断线、刷新及丢失接受响应 | 有执行 ID 时按 ID 读取状态并以 `afterSequence` 续读分页事件；只有操作 ID 时查回原操作或以原摘要重放接受。再从保存的 `syncCursor` 补 changes | 不因恢复失败重新发起模型调用，不拉整个会话来找某个 clientActionId |
| 费用后续更新及其他设备发言 | 费用按原 executionId 更新；当前会话新消息从 changes 拉取。一页不足继续下一游标，不把一页上限当成总量上限 | 不为某次费用变化重新读取全部消息，不拿旧执行的完成结果覆盖当前执行 |

初始消息页和 `syncCursor` 在同一数据库快照下取得。消息提交及其增量记录同事务写入；其他需要同步的结果或费用变化也写入带单调序号的变更记录。已读历史页固定边界，新消息从 changes 合并；客户端以稳定 ID 去重、只接受更新版本，不以时间戳和数组位置判断是否同一消息。

游标失效或变更记录保留期结束时，明确要求重新取得最近一页；不退回全量详情。内容正文异常长时使用可继续展开的正文引用，不能无提示截断原文。服务端索引支持按会话的活动链、消息序号和变更序号读取，执行结果定点查询，不扫描全部历史结果。

完成后的增量读取暂时失败时，保留已确认的回复和草稿，显示同步重试；不能清空可信结果，也不能因此重发。修改确认和建图结果同样按原执行/工具身份合并。

整链路验收使用至少一万条消息，并混入历史分支、执行结果和待核账记录。采集打开、发送接受、上下文准备、提交、完成刷新、刷新页面及 SSE 断线恢复的 SQL、响应体和网络调用：首屏不超过 40 条，每页上限生效，后续响应不随历史总量线性增长，任何环节都不聚合完整图或重新请求通用详情。既验证端点返回量，也核对服务端实际读取范围。

### 5.4 阻塞执行与继续发送

“进入页面”与“允许发送”分别由服务端投影，前端不能以 `busy=false` 推断可以发送。状态返回封闭的原因码、原执行 ID 和可用操作，不把原始凭证或内部错误交给浏览器。

| 服务端事实 | 页面与发送规则 | 后续处理 |
| --- | --- | --- |
| `succeeded`，费用 `pending_evidence/pending_posting` | 回复已提交，允许继续发送，仍执行原余额和模型规则；费用提示附在原回复上 | 后台继续核账、幂等入账；不把执行重新改为运行态，不用停止成功回复来解锁 |
| `awaiting_reconciliation`，仅缺原凭证且无 dispatched/outcome_unknown 调用 | 页面可进入，保留待处理请求并暂停新发送 | 自填 Key 用户在模型设置中补回匹配原配置的凭证，再显式恢复原执行；平台凭证由管理员恢复。凭证不匹配拒绝，不能自动换模型新发 |
| `awaiting_reconciliation`，存在 dispatched/outcome_unknown 调用 | 展示「核对原请求」和「停止原请求后继续」；不直接解锁发送 | 核对只读取/处理原调用证据，不重发不确定的外部请求；有充分结果与检查点证明后才允许原执行恢复。费用凭证本身不等于已证明回复和工具结果完整 |
| 用户明确停止原请求 | 服务端确认 `stopped` 或已经 `succeeded` 后，前端才解除待处理操作并恢复输入；停止响应丢失时查询或重放同一个停止操作 | 停止事务提升所有权 fence、撤销旧租约、处理待审批并保持工具提交的一致性；保留原请求、调用、结果证据和核账事项 |
| 停止和完成提交竞争 | 以服务端同一执行锁的结果为准；完成先提交则保留成功回复，停止先提交则不再接受旧执行的新回复/地图提交 | 不在浏览器抢先标记停止成功；不覆盖后来消息，不生成第二次账单 |

核对后已确定外部结果的原执行，可以沿原身份及检查点继续；仍无法证明结果时继续保留核对，不自动改成失败、不重复请求，也不以超时免收或结案。用户可以选择明确停止以继续对话。

停止不证明上游没有产生费用。本站对停止/失败执行是否收费保持现有规则，原始费用证据及未决审计继续保留并提醒管理员；不能因为执行变为 `stopped/audit_only` 就把仍未知的上游账务视为已核清。迟到的费用证据依原 callId 和原调用 fence 记入原账本，只能更新对应审计/结算，不允许恢复已停止执行或补写旧回复。

前端把当前生成操作与多条历史费用状态分开保存。确认终态后清掉阻塞发送的 pendingGeneration，保留用户尚未发送的草稿和可审计的原操作 ID。每个流、状态响应和费用更新都核对 executionId、序号及本地订阅代次；新请求开始后，旧响应只能更新它自己的卡片，不能重置当前执行或输入框。

阻塞判断同时覆盖当前会话与现有同账号现金队列：其他旧会话中更早的未结束现金请求，也可能挡住本次现金执行。服务端返回有界的阻塞请求摘要和可用的核对/停止入口，页面以请求状态卡解释，不重新引入会话历史栏。不能仅给当前会话解锁，却让新请求永远排队；也不能直接跳过旧请求的状态和结算规则。

必测：成功但待核账后继续发送；缺 Key 补凭证后同执行恢复；未知外部结果拒绝重发；停止后发送及刷新仍可发送；停止响应丢失；停止与完成竞争；旧现金请求阻塞；迟到回复/工具提交被挡而原费用证据仍可入账审计；旧费用更新不覆盖新回复；重复停止、恢复和核账不重复扣费。

## 6. 第二阶段：管理员知识库

### 6.1 管理和内容

后台新增「助手知识库」。只有管理员能创建、编辑、预览、发布、下架和回滚；所有写入使用现有管理员鉴权和 CSRF，普通用户直调同样被拒绝。

第一版支持 Markdown 文章和问答，字段包括标题、分类、正文、关键词/别名、来源说明、修订记录。分类从网站介绍、使用指南、学习理念、路线规划、常见问题开始。暂不加入 PDF/OCR、外部抓取和多租户文档连接器。

正文与版本保存于 PostgreSQL，数据库是内容真源。草稿和未通过索引检查的版本不进入对用户开放的检索。已发布的内容会用于向普通用户回答，管理员编辑页明确显示这一点；机密运维文档不放入这个公开知识库。

现有产品帮助可以作为待审核的初始稿导入；逐条核对当前前端入口后发布，不能照搬已经过期的按钮名称。作者理念由作者提供和审核，开发者不代写成事实。

### 6.2 发布和更新

文章版本不可变，检索索引有独立版本。每篇文章另有单调递增的 `publicationGeneration`（发布代次）、目标文章版本、目标发布状态和当前可见索引；保存草稿本身不改变当前发布内容。

- 每次请求发布、重新索引、回滚或下架，在文章锁内分配新代次。索引任务固定绑定文档 ID、代次、目标版本、内容摘要、模型/tokenizer/分段配置摘要；任务重试不能偷偷取最新正文来替换原输入。
- 新分段与向量写入任务专属的暂存索引，不覆盖当前线上索引。全部校验成功后，切换事务锁定文章，并核对代次、目标版本/状态和预期当前索引仍与任务创建时相符。
- 使用带预期条件的更新，且只接受确切更新一行：只有当前代次仍要求发布该版本、配置匹配且未下架，才能替换可见索引。条件不符时把任务标为已过期；不能无条件重试切换，也不能把文章状态重新写成已发布。
- 可见索引切换与任务成功结果同事务提交。响应丢失后的重复完成先查任务结果；若原成功记录、代次和产物身份均一致，只返回原成功，不再次提升可见版本。不能把这一种重复提交误判成新发布；下架或新代次之后的任务执行则仍为过期，不得重新切换。
- 旧任务晚于新任务完成时，旧任务的代次已失效，即使内容校验通过，也只能保留为不可见的任务产物。任务的失败回写、完成状态和延后清理同样检查代次/产物身份，不能改掉新任务状态或删除当前生效索引。
- 下架事务提升代次、取消目标发布状态、撤销检索可见性并提升知识库可见版本；运行中的任务取消只是加速手段，正确性由上述数据库条件保证。工作进程重启、重复投递和下架后重试也不能重新上架。
- 更新失败时继续使用上一个完整发布版本，后台显示失败原因并允许为仍有效的目标重试；重新选择目标必须新建代次。并发编辑另做草稿版本冲突检测，不覆盖别人刚保存的内容。
- 回滚是选择旧文章/索引内容并申请一个更大的新代次，不回退代次计数。缺少可用索引时先完成重建再切换；旧发布任务不能在回滚后覆盖它。
- 发布切换和下架在事务内提升知识库可见版本。检索缓存绑定此版本和模型配置，读取该版本及可见文档采用一致快照；旧请求晚写入的缓存不会成为新版本缓存。按来源 ID 读取也重新检查可见性。
- 历史回答保留当时的来源版本记录；已经展示过的回答不会因下架自动从聊天中消失。已下架来源的新访问显示已下架。

并发验收必须用可控屏障验证：旧任务 A 晚于新任务 B 完成，B 仍可见；任务索引中下架，A 完成/重启/重试均不能上架；回滚后旧任务失效；重复完成幂等；旧失败回写不覆盖新成功；切换与下架争锁时最终可见状态符合事务先后。不能仅测试单进程任务取消。

### 6.3 检索方式

推荐用 PostgreSQL + pgvector 组合中文关键词和语义检索。pgvector 官方文档支持将向量结果与 PostgreSQL 全文结果结合，并用排名融合排序；这里采用这一思路，不引入独立向量数据库。[pgvector 官方说明](https://github.com/pgvector/pgvector#hybrid-search)

尚未核对生产数据库的 vector 扩展是否已经安装或启用；不能把镜像名称当成确认。实施时先只读检查扩展可用性和版本，在隔离数据库验证迁移及恢复，再按发布流程启用。

原始 Markdown 按标题、段落和问答结构切分，每段带上文章标题、章节路径和版本。大小使用实际 tokenizer 计数，初始目标 256～384 tokens，完整输入不得超出模型的 512 token 容量；标题和特殊 token 也计入。超长段落再拆分，原文完整保留。[分段方法参考](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents)

中文关键词路径必须显式分词：服务端分词后，将标题、别名、关键词和正文词项写入检索字段；不把默认英文分词器当成中文检索。向量和关键词各自召回后做排名融合，去掉大量重复的相邻段，优先返回少量直接有关的完整片段与来源。小规模先用精确向量检索，数据量和耗时测量证明有必要时再加近似索引。

沿用全局助手的 `search_product_help` 工具名称，把该场景的实现接到发布知识库；补充按来源和章节分页读取原文的工具。学习聊天和酒馆原有公开帮助行为不在本阶段顺手改动。旧执行日志仍按原工具结果恢复。

检索结果返回文章、章节、版本、片段和可信的来源标识。前端据服务端字段显示可打开的「参考来源」，不直接信任模型编造的链接。无相关内容返回空结果；回答说明尚未收录，不能把向量最接近的一段硬说成答案。

知识内容只作为参考资料，不能赋予工具权限或覆盖平台策略。学习理念可以影响建议，但不能绕过账号权限、修改确认和费用机制。

### 6.4 本地模型核对

已找到用户指定目录中的模型资产：

- 模型目录：`D:/A1-SmartMaintenance/backend/models/BAAI/bge-small-zh-v1.5`。
- `onnx/model_quantized.onnx`：24,010,842 字节；另有完整精度及其他量化版本。
- `tokenizer.json`、`tokenizer_config.json`、`config.json` 均存在；本地配置为 512 维、最大位置长度 512。
- 本地说明记录它是兼容 Transformers.js 的 BGE ONNX 转换资产；实施时记录模型、tokenizer 和量化文件 SHA256 及许可证，不能仅凭文件夹名称认定版本。

该模型是第一候选，还未做本站检索评测或生产环境推理验收。BGE 的官方用法采用首 token 表征及归一化，查询侧按短查询检索约定处理。A1 现有适配中使用均值池化，因此不直接复制整份 A1 适配器；应依据实际 ONNX 输出与官方实现对齐后验证。[BGE 官方模型说明](https://huggingface.co/BAAI/bge-small-zh-v1.5)

只复用合法可部署的模型资产，MapFlow 使用独立、依赖版本固定的 CPU 推理 worker，限定内部访问；不依赖 A1 业务进程、配置、API Key 或 Windows 的绝对路径。Linux 部署离线装载并校验资产，不在首次用户提问时下载模型。

发布前对浮点和量化版本使用同一份中文本站问句集比较。记录准确率、召回、延迟和内存后选定一种；不同模型/池化/维度的向量不能混入同一个索引。推理不可用时，明确降级到关键词检索并记录健康状态，绝不生成哈希伪向量冒充语义检索。

| 顺序 | 工作 | 验证方式 |
| --- | --- | --- |
| 1 | 固化全局场景边界、默认对话绑定和遗留会话处理 | 先写失败测试：已有多会话、已清空、首次进入、多设备并发；旧标签页新发送与绑定迁移竞争；所有资金通路的新/旧执行入口；旧操作重放和旧执行恢复；角色/Persona/画布/分支/删除越权；实现后跑绿 |
| 2 | 拆出全局页面与模型专用设置 | 检查桌面和手机无历史/新建/通用配置入口，模型设置与原计费仍可操作；学习和酒馆回归 |
| 3 | 三个池子及回访三卡 | 先测稳定选题、跨次轮换、同组不重复、有历史仍可见、草稿不丢、点击不发送、发送后收起、执行中返回不打断 |
| 4 | 平台提示词与工具配置 | 旧角色快照/Persona 不能改变新执行定位；检查长资料、长历史、小窗口、工具往返和恢复后实际模型请求中的平台策略全文；旧执行按冻结版本恢复；全局无画布工具，建图和导航仍能完成 |
| 5 | 长对话、阻塞请求与恢复 | 一万条以上消息覆盖打开、发送校验、准备、提交、完成刷新、断线和刷新恢复；检查有界 SQL/响应与无全量详情请求；并发插入和游标衔接无重漏；第 5.4 节各状态及核对/停止/迟到结果竞争均通过 |
| 6 | 第一阶段 UI 验收 | 320～1440px 截图逐张查看，真实点击模型设置和引导；手机键盘、长回复、回访及加载/空/错误/重试状态 |
| 7 | 独立实施知识库和索引 | TDD 覆盖管理员鉴权、CSRF、草稿不泄露、版本冲突、失败保留旧版、索引恢复、来源权限；用并发屏障验证旧任务晚完成、索引中下架、回滚、重启重试及缓存晚写不会恢复过期可见版本 |
| 8 | 检索与实际回答验收 | 准备至少 40 个有来源的本站问题和 10 个无答案/越界问题；明确标注应命中文章。目标 Recall@5 至少 90%；检索不足先修复。人工检查来源支持结论、无依据时说明、规划与教学分流 |
| 9 | 提交和交付 | 完整前端测试、typecheck、lint（有配置时）、后端测试与 diff 自审；截图和实际通过/失败记录给用户审阅。部署另按发布流程验收 |

阶段一完成不宣称 RAG 已上线，也不依赖先搭好知识库；它先使用已核对的公开产品帮助。阶段二补齐管理员发布与带来源检索后，再让作者理念类问题获得正式资料依据。
