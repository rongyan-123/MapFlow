更新：2026-10-06。当前代码在 `codex/vmq-payment-listener` 分支。此服务仅处理支付通知和订单匹配；MapFlow 的现金额度账本仍由 MapFlow Server 管理。用户没有备用安卓手机，后续验收应继续寻找本地 Linux 安卓方案。

## 服务端状态和规则

`/appPush` 的请求参数为 `type`（1 微信，2 支付宝）、`price`（元，最多两位小数）、`t`（客户端毫秒时间）及 `sign=MD5(type+price+t+通讯密钥)`。服务端要求签名有效、客户端时间与服务端相差不超过 50 秒。相同 `t` 的已处理上报会拒绝重放；安卓端补回调现在保留原 `t`，切换备用通道时用该通道密钥重算签名。超过 50 秒或进程在断网期间死亡的通知没有持久补发保证。

只有渠道、实际金额同时匹配**恰好一笔**待支付订单，且通知时间不早于订单创建时间，才把订单标为已付并调用异步通知。若过去 5 分钟内已有同渠道同金额的已匹配事件，新事件进入待核实，避免旧通知再次出现时误付新订单。合法的连续同金额付款也会因此需要人工核实。

无匹配、多个匹配或近期同金额的通知保存在订单列表，状态 `3`“待核实收款”，`param` 记录原因。此记录不改变用户订单，不发送支付成功回调，不能从 `checkOrder` 取得支付成功结果，也不能点“补单”将核实记录伪装成订单。后台可按状态 `3` 筛选。只有核对收款账户中的实际流水与 MapFlow 申请后，才能通过 MapFlow 管理流程入账。

服务端现在仍使用旧版 V免签的 MD5 通讯签名与 GET 回调。部署时需通过 HTTPS 保护整个链路，设置独立强密钥，修改默认管理密码，并将管理端限制在私网。该通知并非银行或支付平台的可信交易凭据；生产环境不能仅凭它自动给现金额度入账。V免签为单实例 H2 服务，当前去重还依赖 `t` 和服务端本地串行处理；多实例部署或客户端重启后重发为新 `t` 不受完整幂等保证，需进一步引入稳定的通知事件 ID 与数据库唯一约束。

## MapFlow 接入边界

MapFlow 现有充值申请与独立额度账本在 `codex/tavern-wallet-payments-20260930` 开发中，目前是用户声明付款后管理员核实入账，尚无 V免签回调接收路由。接入时由 MapFlow Server 用充值申请 UUID 作为 V免签 `payId` 创建订单；前端不得持有 V免签通讯密钥。`param` 仅传服务器保存的简单标识，避免旧版 V免签的未编码 GET 参数被特殊字符截断。

V免签成功匹配后向 MapFlow 私有回调 URL 发送 `payId,param,type,price,reallyPrice,sign`，其中 `sign=MD5(payId+param+type+price+reallyPrice+通讯密钥)`。MapFlow 接收器必须从数据库查找该 `payId` 对应的充值申请，验证签名、渠道、期望金额及实际支付金额，以 `payId` 和充值申请唯一约束去重，把该申请标记为**待核实**并记录通知证据。不能根据 URL 中的账号、用户的“我已付款”声明或 V免签的状态 `3` 记录直接加额度。管理员核对支付平台实际流水后，才使用现有审批流程及唯一账本约束入账；重复回调只能返回已有状态，不得重复生成额度流水。

## 构建与设备配置

服务端使用 JDK 8，在本目录执行 `mvn test` 和 `mvn package`，构建产物为 `target/mq-0.0.1-SNAPSHOT.war`。启动前设置独立 H2 数据路径、强管理密码和通讯密钥；不要将默认 `admin/admin` 暴露到公网。后台配置微信/支付宝收款码和异步通知地址后再创建真实订单。`/appPush` 的核实记录可在“订单列表 → 待核实收款”查看。

安卓优化版源码位于相邻的 `VmqForks/Nanying666-Vmq-App-Optimized`，使用 JDK 17 和 Android SDK 34，执行 `./gradlew testDebugUnitTest assembleDebug lintDebug`。APK 输出为 `app/build/outputs/apk/debug/app-debug.apk`。在设备上安装后，授予通知使用权和后台运行权限，用“手动配置”输入 `服务端主机:端口/通讯密钥`，点击“检测心跳”和“检测监听”。模拟器访问宿主机本地测试服务时可用 `10.0.2.2`；实体设备应使用可达的 HTTPS 域名。收款通知须来自实际登录的微信/支付宝账号，应用内测试通知只能证明系统回调可达。

## 已执行的验收

在独立的 `/tmp/vmq-acceptance-20260930` H2 数据库、本地 28080 端口和本地 28081 回调接收器上：

1. 创建 `acceptance-1` 测试订单，模拟 `/appPush`，订单变为状态 `1`；本地接收器只收到一条回调。
2. 原样重放该上报，返回“重复推送”，回调计数仍为 1。
3. 上报不存在的 `99.99` 元金额，返回“需人工核实”，后台状态 `3` 列表出现 1 条。
4. 实际金额字符串 `10.00` 的模拟上报完成后，再创建 `10.00` 元订单，实际金额仍可分配为 `10.0`，确认分位金额预留已正确释放。
5. `mvn package` 连同完整测试为 9/9 通过；Android 端 `testDebugUnitTest assembleDebug lintDebug` 为 79/79 通过且 lint 无阻断错误，源码 APK 的自测通知、服务连接及心跳均通过。Java/Kotlin 编译已包含在构建中；Vmq 服务端未配置独立 lint 任务。

以上都是模拟事件。未验证微信/支付宝真实到账通知、真实收款账户流水、MapFlow 回调接收或现金额度入账。完成这四项验收需要一个能稳定运行微信/支付宝且已授权通知读取的本地安卓环境、用户控制的收款账号和一笔实际小额测试交易；当前没有备用实体安卓机。
