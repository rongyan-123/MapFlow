# 技能树节点质量标准

本文档定义技能树节点的质量判据与写法规范，是 `SKILL.md` 阶段 B 第 8 步（每节点推荐深度 + 学习目标 + 关键概念 + 验收证据）的权威参考。AI 拿到本文档即可逐条对照生成，不需要猜测"怎样算合格"。

---

## 1. 五级推荐深度判据

`recommended_depth` 是节点最核心的质量决策——决定了学习者对这个节点"学到什么程度算够"。五种深度从浅到深，每次只能选一个，必须给出具体理由（`depth_rationale`）。

### 1.1 Recognize（认识）

- **含义**：知道这个事物存在、何时需要它、何时可以暂时跳过。学习终点是"场景识别"，不需要动手实现或解释原理。
- **判据**：学习者能说出"这是什么、在什么场景下会用到、可以暂时不学的条件"。
- **典型动词**：识别、列举、辨别、说出。
- **适用场景**：可延后可选分支、技术全景中的替代方案、基础层前置但仅需背景认知的内容。
- **建议 estimated_minutes**：30-60 分钟。

**合格示例**：
```
recommended_depth: "Recognize"
depth_rationale: "该节点是 NestJS 生态中的可选替代方案；学习者只需知道 Fastify 作为 HTTP 底层适配器比 Express 快，在需要高性能场景时考虑即可，不需要深入学习。"
learning_objectives: "[\"能说出 Fastify 适配器与 Express 适配器的区别\", \"能在项目初始时判断是否需要切换为 Fastify\"]"
```

**不合格示例**：
```
recommended_depth: "Recognize"
depth_rationale: "了解即可"
learning_objectives: "[\"了解 Fastify\"]"
```
问题：rationale 未说明为什么是 Recognize 而非 Understand；学习目标用"了解"不可观察。

### 1.2 Understand（理解）

- **含义**：能解释核心机制、边界条件与典型错误。学习终点是"用自己的话讲清楚"，不需要能脱离文档独立写完整实现。
- **判据**：学习者能用自己的话解释原理和适用边界，能比较相关概念的异同，能诊断一个典型错误。
- **典型动词**：解释、比较、画出、分类、推断。
- **适用场景**：影响架构判断的节点、后续节点的前置概念、需要做选型决策但不需要动手选型的内容。
- **建议 estimated_minutes**：60-120 分钟。

**合格示例**：
```
recommended_depth: "Understand"
depth_rationale: "事件循环是 Node.js 异步模型的核心机制；学习者不必能手写 libuv 调度逻辑，但必须能在性能问题时解释为什么某个操作会阻塞事件循环，否则后续所有异步相关节点都会缺乏根基。"
learning_objectives: "[\"能用自己的话解释事件循环的六个阶段及执行顺序\", \"能画出微任务与宏任务的调度时序图\", \"能诊断一个典型的 Promise 时序错误并解释根因\"]"
```

**不合格示例**：
```
recommended_depth: "Understand"
depth_rationale: "这个需要理解"
learning_objectives: "[\"理解事件循环的原理\", \"掌握异步编程\"]"
```
问题：rationale 空洞，"理解"和"掌握"无法被第三方验证。

### 1.3 Use（应用）

- **含义**：脱离逐行照抄后仍能按可靠模式独立完成实现。学习终点是"能产出可运行、可验证的代码或配置"，不需要能在不同约束下自由调整方案。
- **判据**：学习者能在标准环境下独立完成一个最小完整闭环（从搭建到可运行），不需要参考内部源码。
- **典型动词**：实现、搭建、接入、配置、编写。
- **适用场景**：可重复使用的工程能力节点、面试和工作中的高频技能、有明确标准做法的技术点。
- **建议 estimated_minutes**：90-180 分钟。

**合格示例**：
```
recommended_depth: "Use"
depth_rationale: "JWT 认证是后端 API 的高频刚性需求；学习者需要能在 NestJS 项目中独立实现 JWT 登录/验证/刷新全流程，而不是只会跟着教程粘贴代码。"
learning_objectives: "[\"能在 NestJS 项目中独立搭建 JWT 认证守卫\", \"能实现令牌签发、验证与刷新三步骤\", \"能编写集成测试验证受保护路由的认证行为\"]"
```

**不合格示例**：
```
recommended_depth: "Use"
depth_rationale: "需要会用"
learning_objectives: "[\"会使用 JWT\", \"会用 NestJS 做登录\"]"
```
问题：rationale 没有说明和 Understand 的区别；"会使用"太模糊——"会用"可能只是看懂教程，不是独立实现。

### 1.4 Transfer（迁移）

- **含义**：能在不同约束下重新应用核心能力并做出取舍。学习终点是"当场景变量改变时，仍能设计并验证有效方案"。
- **判据**：学习者能在需求/流量/安全/一致性约束改变时调整方案，能对比多种方案并给出取舍理由，能分析生产事故。
- **典型动词**：设计、重构、评估、优化、权衡。
- **适用场景**：生产级关键能力、架构决策节点、涉及多维度权衡的内容。
- **建议 estimated_minutes**：120-240 分钟。

**合格示例**：
```
recommended_depth: "Transfer"
depth_rationale: "数据库事务隔离级别直接影响数据一致性和系统吞吐量；在不同业务场景（金融记账 vs 社交媒体）下需要做出不同的隔离级取舍，学习者必须能在给定业务约束下设计合适的事务策略并验证正确性。"
learning_objectives: "[\"能对比四种隔离级别在脏读/不可重复读/幻读上的取舍\", \"能在给定业务场景下设计事务策略并给出取舍理由\", \"能通过并发测试验证事务边界的正确性\"]"
```

**不合格示例**：
```
recommended_depth: "Transfer"
depth_rationale: "需要深入掌握数据库"
learning_objectives: "[\"深入理解事务\", \"掌握隔离级别\"]"
```
问题：Transfer 是"在不同约束下重新应用"，rationale 没提到任何约束变量；学习目标不包含"设计""评估""优化"等动词。

### 1.5 DeepMastery（深度掌握）

- **含义**：达到可教学、可评审、可贡献上游、可定义新方法论的深度。学习终点是"创造新的知识或标准"。
- **判据**：学习者能编写教学材料让他人学会，能评审他人的设计与实现，能向上游仓库提交修复或特性，能定义团队或社区的最佳实践。
- **典型动词**：教学、评审、定义、贡献、提出。
- **适用场景**：个人核心竞争力节点、面试中的深度展示项、打算长期深耕的方向。
- **建议 estimated_minutes**：180-360 分钟。

**合格示例**：
```
recommended_depth: "DeepMastery"
depth_rationale: "装饰器是 TypeScript+NestJS 的核心范式；达到可教学设计模式如何映射到运行时元数据、能调试 reflect-metadata 源码或为 NestJS 贡献自定义装饰器生态的深度，是该方向的核心竞争力。"
learning_objectives: "[\"能写出教学文档让同事理解装饰器的元数据机制\", \"能评审团队中装饰器使用不当的代码并给出改进方案\", \"能设计自定义参数装饰器并编写测试和类型安全保证\"]"
```

**不合格示例**：
```
recommended_depth: "DeepMastery"
depth_rationale: "装饰器很重要"
learning_objectives: "[\"精通装饰器\"]"
```
问题：DeepMastery 要求"教学/评审/定义"，rationale 只是一个空洞判断；"精通"不可观察——怎么判断一个人是否"精通"？

### 1.6 五级深度速查表

| 深度 | 核心判据 | 标志动词 | 典型 estimated_minutes |
|------|----------|----------|------------------------|
| Recognize | 能识别场景、知道何时需要 | 识别、列举、辨别 | 30-60 |
| Understand | 能解释原理与边界 | 解释、比较、画出 | 60-120 |
| Use | 能独立完成可运行实现 | 实现、搭建、接入 | 90-180 |
| Transfer | 能在不同约束下重新应用 | 设计、重构、评估 | 120-240 |
| DeepMastery | 能教学/评审/贡献上游 | 教学、评审、定义 | 180-360 |

## 2. 深度分层原则

技能树是"浅到深"的拓扑排序，分层同时遵循两条轴：

### 2.1 自底向上：先认识后应用

- `depth_level=1` 的节点负责建立全景认知（大量 Recognize 和 Understand），让学习者先知道"这个领域有什么"。
- 随着 depth_level 递增，Use/Transfer/DeepMastery 比例逐渐上升。
- 最深层的节点（依赖链最末端）才出现 DeepMastery——不是因为"结尾才学"，而是因为这些节点的前置依赖链条最长。

### 2.2 按学习顺序递增难度

- 同一模块内的节点，`depth_level` 小的放在前面（`order_in_level` 小的更先学）。
- 不允许出现"先学深入实践，再学基础概念"的倒置——`difficulty` 数值高的节点其 `depth_level` 不能小于同模块 difficulty 更低的节点。
- 例外：如果 B 是 A 的"可选延伸分支"而非"难度升级"，则 B 可放在 A 的同层或延后一层，difficulty 可不同。

### 2.3 DeepMastery/Transfer 节点放在依赖链较后位置

- 深度目标高的节点通常依赖多个低深度节点，因此自然排在后面。
- 如果发现一个 DeepMastery 节点没有足够的前置依赖（少于 2 个），检查是否遗漏了该方向所需的基础节点。

### 2.4 分层合格/不合格示例

**合格**（4 层，难度递增，依赖合理）：
```
depth_level=1: "认识 AI 应用开发全景" (Recognize)
depth_level=2: "Python 异步编程" (Understand) → "LLM API 调用与流式处理" (Use)
depth_level=3: "RAG 检索增强生成" (Use) → "Agent 工具编排" (Use)
depth_level=4: "生产级 Agent 架构设计" (Transfer)
```

**不合格**（违反"先认识后应用"）：
```
depth_level=1: "实现高性能 RAG 管道" (Use)
depth_level=2: "认识 LLM 基础概念" (Recognize)
```
问题：Use 在 Recognize 前——学习者需要先知道 LLM 是什么才能实现 RAG。

## 3. 学习目标写法

`learning_objectives` 是节点的"做什么才能证明学会了"，不是"要学什么内容"。

### 3.1 基本规则

1. **2-4 条**：太少难以覆盖节点内容，太多考核成本过高。
2. **每条以能力动词开头**：从第 1 节的标志动词表中选取与深度匹配的动词。
3. **"能……"句式**：每条必须是第三人称可观察的行为，不是内部心理状态。
4. **禁止不可验证词**：不得出现"了解""熟悉""掌握""知道""懂得""体会"。这些词没有外在行为标准。

### 3.2 深度-目标匹配规则

| 深度 | 目标中应出现的典型模式 |
|------|----------------------|
| Recognize | "能识别……""能说出……""能列举……" |
| Understand | "能解释……""能比较……（的异同）""能画出……" |
| Use | "能实现……""能搭建……"（最小完整闭环） |
| Transfer | "能在……约束下设计……""能评估……取舍""能重构……" |
| DeepMastery | "能教学……""能评审……""能定义……""能贡献……" |

### 3.3 合格/不合格对比

**合格示例**（Use 级别）：
```
learning_objectives: "[\"能在 NestJS 中从零搭建基于 Passport 的 JWT 认证流程\", \"能编写集成测试验证未认证请求返回 401\", \"能实现角色守卫并编写测试覆盖三种角色场景\"]"
```
为什么合格：每条都能被第三方判断"做到了"。

**不合格示例**（同样的节点）：
```
learning_objectives: "[\"掌握 NestJS 认证机制\", \"了解 JWT 原理\", \"熟悉 Passport 策略\"]"
```
问题：三条全部使用禁止词。

**不合格示例**（目标与深度不匹配——Recognize 却写了 Use 级目标）：
```
recommended_depth: "Recognize"
learning_objectives: "[\"能实现 Redis 缓存加速\", \"能搭建 Redis 集群\"]"
```
问题：Recognize 只需"识别场景"，"实现""搭建"远超目标深度。

## 4. 验收证据写法

`observable_evidence` 是"学习完成后，谁能通过什么方式判断学习者已达标"。不是教学目标，是验收手段。

### 4.1 基本规则

1. **3-5 条**：与学习目标一一对应最好，也可以 1 条证据覆盖 2 条目标。
2. **每条必须是可运行/可演示的具体产物**：代码仓库、测试通过截图、命令行输出、架构图、教学文档。
3. **禁止不可验证描述**：不得出现"完成课程""看完教程""学完 XX 章""理解深入""感觉掌握了"。
4. **禁止循环引用**：不得写成"能完成 XXX-lab"而不描述 XXX-lab 的输出是什么。

### 4.2 可接受的证据形式

| 形式 | 示例 | 适用深度 |
|------|------|----------|
| 运行结果 | "运行 `npm test` 看到 3/3 pass" | Use / Transfer |
| 代码仓库 | "GitHub 仓库中含完整实现，README 记录运行步骤" | Use / Transfer |
| 口头/书面解释 | "能当着导师面在白板上画出事件循环六阶段并解释每阶段内容" | Understand |
| 架构图 | "能画出微服务间消息流转图并标注每条消息的队列名与重试策略" | Transfer |
| 教学材料 | "产出一篇技术分享文档，同事阅读后能独立搭建该组件" | DeepMastery |
| 对比文档 | "能写出 Prisma 与 TypeORM 的选型对比文档，列出 5 种场景下的推荐方案" | Understand / Transfer |
| 代码评审 | "评审 3 份团队成员的认证相关 PR，每条评审意见附带理由" | DeepMastery |

### 4.3 合格/不合格对比

**合格示例**（Use 级别）：
```
observable_evidence: "[\"在 NestJS 项目中运行 curl 登录接口返回 JWT 令牌\", \"运行集成测试脚本，输出 5/5 pass（含正常登录、错误密码、过期令牌三种场景）\", \"GitHub 仓库 README 中记录了搭建步骤和 API 文档\"]"
```

**不合格示例**：
```
observable_evidence: "[\"完成 JWT 认证教程\", \"看完 NestJS 官方文档认证章节\", \"理解了 JWT 工作原理\"]"
```
问题："完成教程"无法证明能力；"看完文档"不是证据；"理解了"不可验证。

**不合格示例**（证据与深度不匹配——Recognize 但要求写代码）：
```
recommended_depth: "Recognize"
observable_evidence: "[\"实现一个 Redis 缓存层并通过测试\"]"
```
问题：Recognize 级别的证据应该是"能列举 Redis 的适用场景"，而不是"实现"。

## 5. 关键概念写法

`key_concepts` 是标签/索引，不是教学内容摘要。用于搜索、关联和快速判断节点覆盖范围。

### 5.1 基本规则

1. **2-5 个**：太少检索不到，太多失去标签意义。
2. **只写该节点独有的核心技术词**：不要把通用概念写进去。
3. **禁止通用词**：不得出现"编程""代码""开发""计算机""软件""技术""知识""学习"。
4. **名词/名词短语为主**：不需要动词，不需要完整句子。

### 5.2 合格/不合格对比

**合格示例**（NestJS 依赖注入节点）：
```
key_concepts: "[\"控制反转(IoC)\", \"Provider 模式\", \"依赖注入容器\", \"NestJS @Injectable\"]"
```
为什么合格：每个词都是该节点独有的核心技术概念，其他节点不会出现相同集合。

**不合格示例**（同样的节点）：
```
key_concepts: "[\"NestJS\", \"后端开发\", \"编程\", \"TypeScript\"]"
```
问题："后端开发""编程"是通用词；"NestJS""TypeScript"几乎每个节点都有，无法区分。

**不合格示例**（过少）：
```
key_concepts: "[\"依赖注入\"]"
```
问题：1 个概念不足以覆盖节点内容，检索时命中概率低。

### 5.3 概念选取技巧

- 问自己：如果只给一个人看这 2-5 个词，他能不能猜出这个节点大概讲什么？能 → 合格；不能 → 太泛。
- 问自己：这组词在整棵树中是否唯一？如果另一个节点也有完全相同的概念集合 → 这两个节点可能需要合并。

## 6. 分层粒度

### 6.1 主干模块粒度

- **数量**：5-10 个主干模块（`category` 数量 = depth_level=1 节点数）。
- **每个模块应有独立主题**：不同 category 之间主题界限清晰，学习者能一眼看出"这部分学什么"。
- **禁止硬凑**：不要把无关主题强行塞进同一层——如果两个主题之间的前置依赖关系不成立，不要用一条边把它们连起来。

### 6.2 单模块节点粒度

- **数量**：每个主干模块 5-12 个节点。
- **相邻层必须有真实依赖**：如果 depth_level=N 的节点和 depth_level=N+1 的节点之间只是"都涉及同一个技术栈"而非"学完前者才能学后者"，不应设为依赖。
- **禁止无关主题硬凑一层**：
  - 合格：`NestJS 模块系统` → `动态模块`（前者是后者的前置）
  - 不合格：`NestJS 模块系统` → `数据库基础`（无直接依赖，只是两个主题放在同一棵树上）

### 6.3 粒度合格/不合格对比

**合格**（依赖真实存在）：
```
"理解 TypeScript 装饰器" (depth_level=2) → "NestJS 中的自定义装饰器" (depth_level=3)
```
装饰器是自定义装饰器的真实前置，后者依赖前者的知识。

**不合格**（依赖不成立）：
```
"Node.js 基础" (depth_level=1) → "数据库设计" (depth_level=2)
```
数据库设计与 Node.js 基础无直接依赖——这是两个独立模块，不应同一边。

## 7. 规模控制

### 7.1 总量范围

- **建议 30-80 个节点**。
- **少于 30**：通常遗漏了就业或项目所需的关键能力。检查方向是否过于狭窄，补充真实工作中需要的相关技能。
- **多于 80**：通常有多个"X 深入""X 进阶""X 高级"节点可以合并到对应的 "X" 节点中（提升深度而非增加节点数）。
- **极简方向例外**：如果学习者明确只要最短路径（如"2 周内学会部署"），可以少于 30——但必须在与学习者确认时明确说明覆盖缺口。

### 7.2 合并规则

当节点数超过 80 时，按以下优先级合并：

1. **"X 深入"/"X 进阶" 并入 "X"**：将深入内容作为 X 节点的更深学习目标，提高 `recommended_depth`，不新建节点。
2. **同类技术合并为一个"选型与应用"节点**：如 Prisma 和 TypeORM 各自一个节点 → 合并为"ORM 选型与应用"，在 learning_objectives 中说明两者对比。
3. **工具类节点合并**：ESLint / Prettier / Husky 各自一个节点 → 合并为"代码质量工具链"。

### 7.3 规模合格/不合格对比

**合格**（45 节点，有深有浅）：
```
5 个主干模块，每个 7-12 个节点，Recognize/Understand 占 40%，Use 占 35%，Transfer/DeepMastery 占 25%
```

**不合格**（合并失败，95 节点）：
```
包含："JWT 基础" (Understand)、"JWT 深入" (Use)、"JWT 高级" (Transfer)
```
问题：JWT 三个节点应合并为一个 "JWT 认证"，深度设为 Transfer。

**不合格**（过少，18 节点）：
```
只有 3 个主干模块，缺少测试、部署、监控相关节点
```
问题：遗漏了后端工程师必须的工程质量环节。

## 8. 自检清单

每次为一个节点撰写五项质量字段（recommended_depth / depth_rationale / learning_objectives / key_concepts / observable_evidence）后，逐条过以下清单：

- [ ] `recommended_depth` 是否匹配节点在树中的位置（依赖链末端才放 DeepMastery）？
- [ ] `depth_rationale` 是否说明了"为什么是这个深度"而非空洞的"很重要"？
- [ ] `learning_objectives` 中的每条是否可用"能……"开头？是否有不可验证词？
- [ ] `learning_objectives` 中的动词是否与 `recommended_depth` 的标志动词匹配？
- [ ] `observable_evidence` 的每条是否描述了具体产物（不是"完成课程""看完文档"）？
- [ ] `observable_evidence` 是否与 `recommended_depth` 匹配（Recognize 不应要求写代码；Use 不应只要求口头解释）？
- [ ] `key_concepts` 是否 2-5 个？是否都是该节点独有的技术词（不含"编程""代码"等通用词）？
- [ ] 五项之间是否自洽？例如 `recommended_depth="Recognize"` 但 `learning_objectives` 出现"能实现……"？
